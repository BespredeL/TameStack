Безопасность является фундаментальным приоритетом TameStack, так как приложение оперирует правами суперпользователя (`root`) на критических инфраструктурных серверах.

---

## 🎯 1. Модель угроз (Threat Model)

### Векторы атак и риски
1. **Man-In-The-Middle (MITM) на SSH-уровне**: подмена публичного ключа сервера в процессе рукопожатия, перехват учетных данных или команд.
2. **Компрометация локального хранилища**: несанкционированный доступ к файлу базы данных SQLite на машине пользователя.
3. **Command Injection**: внедрение вредоносных управляющих символов и команд через пользовательские поля (домены, имена баз данных, пути).
4. **Утечка секретов в логи**: попадание паролей, токенов и приватных ключей в файлы логов или вывод Wails событий.
5. **Случайные деструктивные действия**: непреднамеренное удаление пользовательских данных, порча конфигураций или потеря доступа по SSH/Firewall.

## 🔑 2. Защита SSH-соединений

### 2.1. Строгая проверка SSH Host Key
- **Полный запрет** на использование `ssh.InsecureIgnoreHostKey()`.
- Использование специализированного файла `known_hosts` (в формате OpenSSH), расположенного в защищенной директории приложения.
- При первом подключении к новому серверу:
  - Вычисляется SHA-256 хэш (fingerprint) полученного публичного ключа.
  - Соединение приостанавливается с требованием явного подтверждения пользователя в UI (показ отпечатка ключа).
  - Только после подтверждения хост-ключ сохраняется в `known_hosts`.
- При несовпадении сохраненного ключа с полученным:
  - Соединение **немедленно разрывается**.
  - В UI выдается предупреждение высшего приоритета о возможной атаке MITM (Host Key Verification Failed).

### 2.2. Защита приватных ключей и паролей
- Приватные ключи с `passphrase` расшифровываются исключительно в оперативной памяти в момент установления соединения.
- Закрытые ключи пользователей никогда не передаются на сторонние сервисы и не кешируются в открытом виде.

## 🔐 3. Локальное хранение секретов (Local Secret Storage)

### 3.1. Криптографический алгоритм
Все пароли и приватные SSH-ключи, сохраняемые в локальной базе SQLite, шифруются с помощью:
- **AES-256-GCM** (Galois/Counter Mode) — обеспечивает конфиденциальность и аутентичность шифротекста (защита от подмены).
- Уникальный 12-байтовый криптографический `Nonce` генерируется для каждой отдельной записи через `crypto/rand`.

### 3.2. Формирование мастер-ключа (Master Key Derivation)
- При первом запуске генерируется случайный 32-байтовый машинный ключ, который хранится под защитой системного хранилища секретов там, где оно доступно (Windows DPAPI, привязка к учетной записи пользователя с прикладной энтропией); на остальных платформах ключ сохраняется в файле с правами `0600`. Ключ хранилища формируется из этого машинного ключа и локального salt-файла через **HKDF-SHA256**.
- Предусмотрена возможность установки пользовательского мастер-пароля: в этом случае ключ хранилища формируется из парольной фразы и salt через **PBKDF2** (HMAC-SHA256, 200 000 итераций), и секреты доступны только после разблокировки.

### 3.3. Контейнер шифрования базы данных целиком (опционально)
- Оператор может включить шифрование всей базы: `TameStack.db.enc` — почанковый контейнер, где каждый блок 64 КиБ запечатан **AES-256-GCM** под ключом, производным от уже настроенного мастер-пароля хранилища (п. 3.2) через **PBKDF2** (HMAC-SHA256, 200 000 итераций) и случайный 16-байтовый salt контейнера, хранимый в его заголовке; ключ контейнера доменно отделён от ключа хранилища, хотя оба происходят из одного пароля. Отдельного пароля для базы нет — шифрование можно включить только когда мастер-пароль уже задан. Nonce чанков формируются счётчиком от случайного базового nonce каждого поколения; заголовок аутентифицируется как дополнительные данные (AAD).
- Мастер-пароль требуется до открытия базы: стартовый экран расшифровывает контейнер в рабочую копию, и все сервисы поднимаются только после успешной разблокировки. Неверный пароль обнаруживается по провалу аутентификации GCM первого чанка; после открытия базы хранилище разблокируется тем же паролем прозрачно.
- Во время работы приложения в подкаталоге `run\` защищённого каталога данных существует открытая рабочая копия; она перепечатывается в контейнер каждую минуту (при наличии изменений) и при корректном завершении, после чего удаляется. После некорректного завершения рабочая копия сохраняется до следующей успешной разблокировки паролем. Таким образом, контейнер защищает от офлайн-кражи каталога данных, но не от вредоносного кода, работающего в активной сессии пользователя.

## 🛡 4. Защита от Command Injection

### 4.1. Валидация входных данных
Все значения, которые могут попасть в удалённый шелл, проходят строгую валидацию по белым спискам (`internal/ssh/safe.go`) — по категории, а не по конкретному экрану интерфейса:
- **Доменные имена**: строгая проверка по RFC 1123 (`^[a-zA-Z0-9]([a-zA-Z0-9-]{0,61}[a-zA-Z0-9])?(\.[a-zA-Z0-9]([a-zA-Z0-9-]{0,61}[a-zA-Z0-9])?)*$`).
- **Имена пользователей Linux/БД и имена баз данных**: `^[a-zA-Z_][a-zA-Z0-9_-]{0,31}$`; для host-значений (`localhost`, `%`) отдельный валидатор.
- **Имена systemd-юнитов, селекторы логов, глаголы/протоколы/порты файрвола, режимы chmod, образы Docker, версии PHP, charset/collation**: для каждой категории свой валидатор; значение вне разрешённой грамматики отклоняется, а не «экранируется и выполняется».
- **Параметры джейлов Fail2ban**: имена джейлов, порты (числовые или имена служб), названия фильтров, счетчики попыток, интервалы времени (`10m`, `24h`, `7d`) и списки исключений IP/CIDR (`ignoreip`) проходят строгую валидацию по белым спискам перед записью в `jail.local` или передачей в `fail2ban-client`.
- **Задания Cron и контекст пользователей**: синтаксис расписаний проверяется по стандарту cron; crontab-файлы изолированы по пользователям ОС (`root` и непривилегированные пользователи) для исключения несанкционированного повышения привилегий.
- **Пути файловой системы**: нормализация через `filepath.Clean`, блокировка traversal-последовательностей (`../`), переводов строки и неабсолютных путей.

Аргументы инструментов ИИ проходят те же валидаторы, что и ввод интерфейса: значение вида `log_type=$(id)` отклоняется до формирования команды.

### 4.2. Безопасное экранирование аргументов
При формировании SSH команд:
- Любая подстановка значения выполняется единственной функцией `ssh.ShellEscape` (`internal/ssh/builder.go`) со строгой POSIX-семантикой одинарных кавычек — `$(...)`, обратные кавычки и `$VAR` внутри результата не раскрываются. Go-формат `%q` для шелл-кавотинга не используется.
- Внешние слои не могут передать в модуль произвольную командную строку. Инспекция только для чтения идёт через типизированный API `internal/modules/security/readonly.go`: шаблоны команд, списки файлов логов и лимиты (не более 200 строк за вызов) принадлежат коду, а файлы с секретами (приватные ключи, `shadow`, `.env`, `master.key`) исключены из чтения ИИ.
- Административный SQL для MySQL/PostgreSQL передаётся клиенту по stdin (`ExecStdin`), а не встраивается в шелл-аргумент; идентификаторы валидируются и кавотируются как SQL-идентификаторы.

### 4.3. Разрешение символьных ссылок перед записью
Перед записью конфигурационного файла путь разрешается на сервере через `readlink -f` (`SSHClient.ResolveRemotePath`, `internal/ssh/resolve.go`), и политика безопасности проверяет уже разрешённую цель. Поэтому символьная ссылка внутри разрешённого каталога (например `/var/www`) не может направить запись в защищённое место вроде `/etc/shadow`.

## 🧠 5. Approval Gate для инструментов ИИ

- Каждый зарегистрированный инструмент объявляет уровень риска и признак изменения данных. `SecurityGate.RequiresHumanApproval` (`internal/ai/policies/security_gate.go`) требует подтверждения, если инструмент изменяющий **или** если его `RiskLevel` отличается от `safe` — ошибочно помеченный инструмент всё равно уходит на подтверждение пользователю.
- Цикл чата разделяет вызовы инструментов на выполняемые автоматически и требующие подтверждения; без подтверждения выполняются только безопасные (`RiskSafe`, не изменяющие) инструменты чтения.
- Проверка выполняется не только в цикле чата: `Registry.Execute` отказывает любому инструменту, требующему подтверждения, поэтому вызов, созданный в обход классификатора, отклоняется до запуска обработчика. Для подтверждённого исполнения предназначен `Registry.ExecuteApproved`.
- Каждый исполненный инструмент пишет строку аудита (`ai_tool_audit`): имя, уровень риска, санитизированные аргументы, длительность, успех и признак того, что исполнение подтвердил человек. Отклонённые вызовы в аудите как исполненные не появляются.
- Изменяющие инструменты (`prepare_config_diff`, `propose_service_restart`) в чате не выполняются: цикл останавливает их и помечает как требующие подтверждения. Реальное применение изменений идёт через задачи Task Engine (`SubmitRequiresApproval`), которые оператор подтверждает явно. Связка «подтверждение в чате → запуск задачи» сейчас не замкнута: у отложенного подтверждения чата нет пути запуска из интерфейса, поэтому такие изменения остаются заблокированными, а не выполняются молча.

## 🧹 6. Санитизация логов (Log Scrubbing)

Встроенный фильтр логов (`LogScrubber`) перехватывает все сообщения Task Engine перед отправкой на фронтенд и записью в БД:
- Автоматически маскируются закрытые SSH ключи (`-----BEGIN.*PRIVATE KEY-----`).
- Маскируются значения параметров, содержащие ключи `password`, `secret`, `token`, `passphrase`, `api_key`.
- В логах отображается безопасный плейсхолдер: `[REDACTED_SECRET]`.

## ⚠️ 7. Защита от деструктивных действий (Destructive Action Safeguards)

1. **Режим предварительного аудита (Dry-Run / Audit First)**:
   При первичном подключении к серверу TameStack выполняет только чтение параметров (инспекцию). Никакие пакеты не устанавливаются и конфиги не правятся без явной команды пользователя.
2. **Обязательный бэкап конфигураций**:
   Перед изменением любого конфигурационного файла (`nginx.conf`, `php.ini`, виртуальные хосты) создается его резервная копия с временным штампом: `/etc/nginx/sites-available/domain.conf.TameStack.bak.<timestamp>`.
3. **Защита от потери SSH/Firewall доступа**:
   При настройке правил UFW/Firewall правило для активного порта SSH пользователя добавляется и верифицируется в первую очередь. При смене порта SSH старый порт остается активным до подтверждения успешного соединения по новому порту.
4. **Запрет скрытых фоновых обновлений**:
   Запрещен автоматический неконтролируемый запуск `apt upgrade -y` или `dist-upgrade` без подтверждения списка обновляемых пакетов.
5. **Двухэтапное подтверждение**:
   Опасные операции (удаление сайта, удаление базы данных, удаление контейнера, перезагрузка сервера) требуют явного подтверждения в модальном диалоге с вводом имени удаляемого ресурса.

## 🔄 8. Модель доверия обновлений приложения (Self-Update Trust Model)

1. **Только фиксированный HTTPS-источник**:
   Метаданные обновлений запрашиваются исключительно по HTTPS через GitHub Releases API данного репозитория (`api.github.com`). Никаких зеркал, сторонних конечных точек или настраиваемых пользователем URL обновления.
2. **Обязательная верификация SHA-256**:
   Перед запуском или установкой скачанного архива его SHA-256 хэш сверяется с хэшем из GitHub asset API. Если хэш отсутствует или не совпадает, обновление прерывается — непроверенный бинарный файл никогда не применяется (fail-closed).
3. **Безопасное извлечение архива**:
   Из архива релиза извлекается только один исполняемый файл верхнего уровня; записи, содержащие пути, игнорируются во избежание path traversal за пределы каталога обновления.
4. **Атомарная замена бинарника**:
   Текущий исполняемый файл переименовывается, верифицированный бинарник перемещается на его место, а старая копия автоматически восстанавливается в случае ошибки. Оставшиеся старые копии удаляются при следующем запуске приложения.
5. **Отсутствие скрытой эскалации прав**:
   Процесс обновления пишет только внутри собственной директории приложения и никогда не запрашивает права администратора; если каталог недоступен для записи, обновление завершается с ошибкой, а ручная установка остается доступной.
6. **Дисциплина перезапуска**:
   Перезапуск обновленного бинарного файла происходит только после того, как процедура завершения закрыла все дескрипторы и запечатала зашифрованный контейнер базы данных.
